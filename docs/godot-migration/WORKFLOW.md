# Процесс маленьких задач для агента и человека

## Цель цикла

Каждый цикл заканчивается небольшим проверяемым результатом: работающей функцией,
одним понятным файлом, подключённой сценой или устранённым конкретным дефектом.
Человек может прочитать diff и объяснить его без изучения большого нового модуля.
Исследование и планирование занимают столько места, сколько нужно ближайшему шагу.

## Старт или возобновление

1. Прочитать AGENTS.md, индекс этого пакета, актуальные RULES.md, этот процесс
   и STATUS.md. Проверить git status и имеющийся diff.
2. Определить назначенную задачу, её зависимости и состояние ревью.
   Прочитать карточку и только связанные разделы видения/исходники.
3. Если есть незавершённый шаг, восстановить его по STATUS.md и diff.
   Не переписывать уже сделанное и не считать отсутствие сообщения принятием.
4. Учесть новые сообщения пользователя. Прямое поручение выполнить конкретный
   шаг разрешает этот шаг без дополнительного подтверждения.

В той же сессии не перечитывать уже известные неизменившиеся документы.
Достаточно учитывать новые сообщения, актуальную ревизию правил и изменения
точки продолжения. После потери контекста снова выполнить короткий старт.

## Размер шага

Ориентир — одна функция, один небольшой файл или одно наблюдаемое поведение.
Обычно затрагивается один производственный файл плюс необходимая проверка.
Связанные scene/script/config могут составлять один шаг, если по отдельности
результат нельзя проверить. Это объясняется в карточке.

Число файлов и строк — сигналы, а не цель. Документация учёта не входит
в размер игрового изменения. Нельзя сжимать код, строить цепочку наследования
или раскладывать одну простую операцию по многим файлам ради формального лимита.
Если diff перестаёт быть легко обозримым, уменьшить задачу до самостоятельного
результата и оставить остальные части в очереди.

## Выполнение одного шага

1. Зафиксировать в карточке цель, изменяемые файлы, предусловия, ожидаемое поведение
   и способ проверки. Для нового шага пользоваться [шаблоном](tasks/TEMPLATE.md).
2. В STATUS.md перевести единственную активную задачу в in_progress.
3. Реализовать только её результат. Если обнаружена необходимая дополнительная
   зависимость, описать и выделить её в маленькую задачу; не расширять незаметно
   текущий шаг до целой подсистемы. Сохранить уже проверяемую часть.
4. Проверить подходящим способом. Для изменения правила — значимый тест поведения;
   для сцены — запуск и проверка сценария; для документа — ссылки и согласованность.
   Зафиксировать команды, рабочую папку, результаты и непроверенные части.
5. Просмотреть diff самому: простота, владение состоянием, реальные границы,
   отсутствие случайных соседних изменений.
6. Обновить STATUS.md: awaiting_review, точный результат, проверка,
   основание кода (commit и локальный diff) и следующий возможный шаг.
7. Представить человеку короткий пакет ревью и завершить цикл.

В одном цикле не нужно писать документ-исследование для каждого метода,
строить инфраструктуру для гипотетических потребностей или прогонять несвязанные
полные наборы тестов повторно. Известная проблема baseline описывается конкретно,
а новое падение проверяется и устраняется.

## Ревью

| Статус | Значение |
| --- | --- |
| planned | Шаг описан, но его предпосылки ещё не подтверждены |
| ready | Зависимости приняты, шаг можно назначить |
| in_progress | Выполняется; одновременно только один шаг |
| awaiting_review | Результат создан и проверен, ожидается ревью |
| changes_requested | Есть замечания; следующий цикл исправляет этот же шаг |
| accepted | Пользователь явно принял результат или поручил продолжить от него |
| blocked | Продолжение зависит от конкретного отсутствующего решения/возможности |
| cancelled | Шаг снят или заменён; сохранена причина и ID замены, если есть |

Обычный цикл допускает не более одного реализованного, но не принятого шага.
После awaiting_review агент может подготовить краткую карточку следующего шага
или прочитать нужные файлы, но не начинает следующий кодовый diff без поручения
или принятия предыдущего. Это желаемый пользователем ритм ревью.

Принятие хранится с датой и краткой ссылкой на смысл сообщения пользователя.
Успешный тест, коммит и истекшее время не означают принятия человеком.
Замечания исправляются в том же ID задачи; историю ревью не подменять новым ID.
Пользователь может явно разрешить пакет нескольких шагов или иной ритм;
область исключения записывается в STATUS.md.

## Пакет ревью

- ID задачи и одно предложение о результате.
- Изменённые игровые файлы и ключевые места для чтения.
- Почему выбран такой простой способ и какую границу он сохраняет.
- Команды/сценарии проверки с результатом; материальные ограничения.
- Следующий маленький шаг, который станет доступен после принятия.

Для функции достаточно короткого объяснения; пересказывать весь diff не нужно.
Если изменение в сцене существенно для игрока, приложить доступное визуальное
подтверждение или точный ручной сценарий. Не сообщать, что ручное ревью состоялось,
если оно ещё не проводилось.

## Долговременная память и корректировки

STATUS.md — актуальная точка продолжения. ROADMAP.md — план. RULES.md —
действующие нормы. DECISIONS.md — основания выбора. Карточка задачи — её контракт.
Не вести вторую независимую таблицу статусов в комментариях или задачах.

STATUS.md держать коротким: активный результат, ближайшие 1–3 шага и последние
3–5 завершённых записей. Более старую историю переносить в history/YYYY-MM.md
в этой папке с указателем из STATUS.md. Архив хранит факты результата и ревью,
но не является второй текущей очередью. Его не нужно читать при каждом старте.

Новое постоянное указание пользователя записать в RULES.md с устойчивым ID,
увеличить ревизию и отметить изменения в STATUS.md. Если оно меняет архитектуру
или продукт, обновить DECISIONS.md и затронутый раздел видения. Если требуется
переделать уже принятый код, создать отдельный маленький шаг с причиной;
историческое принятие остаётся фактом.

Локальную обратную связь о текущей функции сохранить в её записи ревью.
Не превращать каждое замечание к имени переменной в глобальное правило.
При конфликте документов применить последнее прямое указание пользователя
и исправить противоречие в рамках текущей работы.

## Прерывание сессии

Перед остановкой сохранить: активный ID и статус, сделанное и оставшееся,
затронутые файлы, результаты проверок, открытые замечания, точный следующий шаг
и ревизию правил. Неработающий промежуточный diff обозначить явно. При возобновлении
проверить фактические файлы; запись не заменяет проверку рабочей копии.

Прогресс измеряется принятыми поведениями и работающим игровым циклом.
Строки кода, количество документов и потраченные токены не заменяют результат.
